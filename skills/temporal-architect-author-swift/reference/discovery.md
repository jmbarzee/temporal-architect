# discovery

The Swift signals the design skill's [reverse engineering](../../temporal-architect-design/reference/reverse-engineering.md#language-signals) reads code by. Call sites read backward through the [reference index](../SKILL.md#reference-index): `context.executeActivity(C.Activities.Name.self, …)` is an `activity` call, `context.executeChildWorkflow(W.self, …)` a `workflow` call, a `throw ApplicationError(…)` out of `run` a `close fail`, and a `signalWorkflow` on a child handle or a `signal` on `context.getExternalWorkflowHandle(W.self, id:, runId:)` a `signal` send, whose `id:` is constructed when `W.id(…)` renders it, learned when a variable holds it, and `parent` from `context.info.parent` ([signal-send.md](./signal-send.md)). Names read back through [Wire names](../SKILL.md#wire-names), payload types through [types.md](./types.md), and a call's options through [options.md](./options.md): a `static let` every call of one definition starts from is its `default_options:`, and the fields a call's `var` copy changes are its `options:`. Paths below are in swift-temporal-sdk source at `1.5.0` (`Sources/`).

## Project roots

- A `Package.swift` that depends on `.package(url: "https://github.com/apple/swift-temporal-sdk…")` and the `Temporal` product, or an Xcode project with that package reference, marks a root that uses Temporal. A manifest names no module path: the repo's remote without the scheme (`github.com/acme/orders`), else the repo path, is the path `twf mod init` takes; ask when neither fits. Each `.target` or `.executableTarget` is one `.twf` package; a `.testTarget` is not part of the design.

## Registration

- `TemporalWorker(configuration:target:transportSecurity:activityContainers:activities:workflows:)` (`Temporal/Worker/TemporalWorker+HTTP2Posix.swift:37-44`) starts a worker on its configuration's `taskQueue` in its `namespace`, both required (`Temporal/Worker/TemporalWorker+Configuration.swift:391-393`); the client's own `namespace`, `"default"` when unset (`Temporal/Client/TemporalClient+Configuration.swift:113`), is not the worker's. A configuration built by `init(configReader:)` reads `worker.namespace` and `worker.taskqueue` from config (`:456-464`, `Temporal/Statics/ConfigKeys+Worker.swift:19,21`), and a queue from `ProcessInfo.processInfo.environment` cannot be resolved from code either: ask, or leave it to the stitch's topology. Its other properties read back through [worker.md](./worker.md#worker-options) into the namespace worker's `options:`.
- The types one `TemporalWorker` registers make one `worker` block ([worker.md](./worker.md#registration)), annotated `@sdk(swift, "<path>")` with the file that registers them. An `enum` holding `workflows`, `activities(…)` and `configuration(…)` is that set, shared by the worker process and its tests: `enum BatchTypes` is `worker batchTypes`, and its `Worker.swift` is the path, from the directory of the nearest `twf.mod`. With no `TemporalWorker` built from it in the slice, there is no namespace to recover, and its `configuration`'s default `taskQueue` is only the queue the stitch's topology should confirm. A test's worker gives the test's queue and namespace, not the deployment's, and workflows only a test registers (the corpus's `AwaitOneFixtures.swift`) are fixtures, not the design. A container property only tests set (the corpus's `hold`, `nil` by default) is a test seam, not design: an activity body that only awaits one is empty.
- `workflows:` lists `@Workflow` structs, each its `.twf` workflow named by `@Workflow(name:)`, else the struct's name. `activities:` takes definitions, usually a container's `allActivities`, and `activityContainers:` containers, registering each `@Activity` method of an `@ActivityContainer`, named by `@Activity(name:)`, else the method name with its first letter capitalized (`chargeCard` → `ChargeCard`).
- A workflow's `run(context:input:)` takes one input ([workflow-def.md](./workflow-def.md)). A nested `Input`, or a struct named for its definition (`<Name>Input`, as the corpus's `CounterInput` and options.md's `ChargeCardInput`), is several params, its fields in declaration order. This is a naming heuristic: when the struct is also used as a value elsewhere in the design, keep it one param. Any other type is one param, named for what it holds, since the name never reaches the wire; `input: Void` is none. An `@Activity` method's one parameter reads the same ([activity-def.md](./activity-def.md)). Its return is the `.twf` return; a struct made only to return it is `-> (A, B)`, its fields in order. This too is a heuristic: when the struct is also used as a value elsewhere in the design, keep it one return.
- An `@WorkflowSignal`, `@WorkflowQuery` or `@WorkflowUpdate` method of the struct declares a `signal`, `query` or `update` of that workflow, named by its `name:`, else the method name capitalized. Its params read as `run`'s input does, its result the query's or update's return, and its body the method's statements less the arrival record (`xs.add(…)`, or a counter's `acks += 1`). An `@WorkflowQuery` property is a query with no params returning that `var`, which is also `state:` ([query-handler.md](./query-handler.md)). The stored `var`s the handlers and `run` share, less its `Arrivals` and arrival counters, are its `state:`; a `Bool` set by a handler and awaited by `context.condition` is a `condition` ([condition.md](./condition.md)). The macro's `description:` and `unfinishedPolicy:` give `description` and `unfinished_policy`.
- An `@WorkflowUpdate(validator:)` method (`Temporal/Macros/WorkflowMacro.swift:185-190`), an `@Activity(dynamic: true)` method (`Temporal/Macros/ActivityMacro.swift:49`), a continue-as-new onto another type (`makeContinueAsNewError(workflowType:…)` or `(workflowName:…)`, `Temporal/Worker/Workflow/WorkflowContext.swift:1088,1122`), and a `context.condition { context.allHandlersFinished }` before `run` returns, which is no `condition`, have no `.twf` form: record each in prose with its `file:line`.
- A `static func id(…)` on a workflow struct, returning an interpolated string that every start of it passes as `id:`, is its `id_scheme:`: each hole is the function's argument, named from the workflow's params (`ShipItem.id(orderId: order.id, itemId: item.id)` → `"ship-{order.id}-{item.id}"`). A `static func startOptions(…)`'s `idReusePolicy` and `idConflictPolicy` are its `default_options:` ID policies ([workflow-def.md](./workflow-def.md#id_scheme)).
- A queue built by an instance-key function (`static func taskQueue(sandboxId:)` → `"sandbox-\(sandboxId)"`) is a [family](./worker.md#per-instance-worker-families) worker.
- Nexus is unsupported: the SDK's worker never polls Nexus tasks and a workflow has no Nexus call ([nexus.md](./nexus.md)), so no Swift code reads back as a `nexus service`, a `nexus` call or `detach nexus`.
- A `TemporalWorker` built behind a factory or a `ServiceGroup`: follow it to the initializer.

## Concurrency

| Swift | `.twf` |
|------|--------|
| `@WorkflowSignal` / `@WorkflowUpdate` method whose body ends with `xs.add(…)` on an `Arrivals` | handler, its body less the `add` ([signal-handler.md](./signal-handler.md), [update-handler.md](./update-handler.md)); a counter it increments (`acks += 1`) and a waiter decrements once per take (`acks > 0` … `acks -= 1`) is an `Arrivals<Void>`, while one never decremented, or reset, is plain `state:` |
| `try await context.take(\.xs)` | `await signal\|update Name -> (…)`, an input struct's fields read as its names; `Arrivals<Void>` binds none ([await-signal.md](./await-signal.md)) |
| `let t = xs.begin()`, then `async let p = context.take(\.xs, at: t)`, `try await p` later | `promise p <- signal\|update Name` ([promise.md](./promise.md)); `async let p = context.take(\.xs)` without the ticket too, with a comment that it begins waiting only when `run` next suspends |
| `async let p = context.executeActivity(…)` or `executeChildWorkflow(…)`, `try await p` later; `async let p: Void = context.sleep(for: d)` | `promise p <- activity\|workflow …`, `promise p <- timer(d)` ([promise.md](./promise.md)) |
| `async let` per branch, then one `try await (a, b)`; `withThrowingTaskGroup` with `addTask` in a `for`, then `waitForAll()` | `await all`, branches in binding order; a `for` fan-out inside ([await-all.md](./await-all.md)) |
| one `context.condition` over each case's ready check, then an `if` chain in check order where the winner `claim()`s, `acks -= 1`s or `try await`s and each losing message case `leave(t)`s | `await one`, cases in that order ([await-one.md](./await-one.md)) |
| … a case whose check is a `Flag` a sleeping child of the round's task group sets, the group `cancelAll()`ed when another case wins | a `timer(d)` case: an inline timer, cancelled when it loses |
| … a case whose check is a `Flag` set by an `async let` bound before the rounds (after `context.sleep(for: d)`, as the corpus's `BoundDeadline` does, or by its `defer` around a call without `.abandon`) | `promise p <- timer(d)\|activity …\|workflow …` at that binding and a `p:` case, which losing a round never cancels (spec 06) |
| … a case whose check is a `Flag` a run-scope `async let p = { defer { done.isSet = true }; return try await context.executeActivity\|executeChildWorkflow(…) }()` sets, its options' `cancellationType: .abandon` | an inline `activity` or `workflow` case, or a nested `await all:` when the closure awaits several calls, left running when it loses (spec 06) |
| `do { try await context.timeout(for: d) { try await context.condition { c } }; … } catch { … }` | `await one` with a `timer(d)` case, then a `c` case: it cancels the condition once the sleep returns, so the timer wins a tie (`Temporal/Worker/Workflow/InternalWorkflowContext.swift:151-211`); the `catch` runs the timer case's body, the code after the `timeout` the condition's |
| `try await group.next()` over a task group's racing children | `await one`, with a comment that the first to finish wins, not the first listed: a timer or activity result of the same workflow task beats a signal ([await-one.md](./await-one.md)) |
| `try await context.condition { $0.flag }` alone | `await flag` ([condition.md](./condition.md)); a handler's `flag = true` / `false` is `set` / `unset` |
| `_ = try await context.startChildWorkflow(W.self, options: ChildWorkflowOptions(parentClosePolicy: .abandon, cancellationType: .abandon), input: …)`, its handle never awaited | `detach workflow` ([detach.md](./detach.md)); with `.abandon` for `parentClosePolicy` alone the caller's cancellation still reaches the child, so record that in prose |
| `let h = try await context.startChildWorkflow(…)`, `async let p = h.result()` | `promise p <- workflow …`, the handle head of its `signal h.Name(…)` sends ([signal-send.md](./signal-send.md)) |
| a call with `try await` at once | synchronous call |
| `throw try await context.makeContinueAsNewError(options:input:)` | `close continue_as_new(args)`, the input's fields as args ([close.md](./close.md)) |
| `try await context.sleep(for: d)` | `await timer(d)` ([await-timer.md](./await-timer.md)) |
| `if context.patch("id") { new } else { old }` | the `new` branch alone; a `context.deprecatePatch("id")` is dropped: a patch ID is code, never design ([versioning.md](./versioning.md)) |
| `ActivityExecutionContext.current?.heartbeat(details: x)` in an `@Activity` method | `heartbeat(x)` in the activity body ([heartbeat.md](./heartbeat.md)) |

## Codegen

- No forward variant generates code ([SKILL.md](../SKILL.md#orient)): the macros expand at compile time, so read the attributed source, never the expansion. `@Workflow` makes the struct a `WorkflowDefinition` (`Temporal/Macros/WorkflowMacro.swift:43,46`); `@ActivityContainer` adds a nested `Activities` with one definition per `@Activity` method, and `allActivities` (`TemporalMacros/ActivityContainerMacro.swift:155-158`); each handler macro nests a struct named for its method (`TemporalMacros/WorkflowSignalMacro.swift:94,113`), which a send's `signalType:` names.
- A `WorkflowDefinition` or `ActivityDefinition` conformance written by hand reads as the macro's would, named by its `static var name`, else the type's name (`Temporal/Worker/Workflow/WorkflowDefinition.swift:101-103`, `Temporal/Worker/Activities/ActivityDefinition.swift:88-90`).
- `SwiftProtobuf` messages travel through the default converter's `JSONProtobufPayloadConverter` and `BinaryProtobufPayloadConverter` (`Temporal/Converters/DefaultPayloadConverter.swift:30,33`): the payload types come from the `.proto` that `protoc-gen-swift` or the `SwiftProtobufPlugin` build plugin compiles.
- No Nexus contract is generated: the SDK has no Nexus.
- `Package.swift`'s `plugins:` name any other generator.
