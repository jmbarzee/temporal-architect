# discovery

The Elixir and Erlang signals the design skill's [reverse engineering](../../temporal-architect-design/reference/reverse-engineering.md#language-signals) reads code by. Call sites read backward through the [reference index](../SKILL.md#reference-index): `start_activity` is an `activity` call, `start_child_workflow` a `workflow` call, `start_timer` a timer, and `complete_workflow_execution`, `fail_workflow_execution` and `continue_as_new_workflow` the run's `close` ([close.md](./close.md)); loops and branches read back through [control-flow.md](./control-flow.md). Names read back through [Wire names](../SKILL.md#wire-names). Erlang spells the same API: `-include_lib("temporal_sdk/include/workflow.hrl")` declares the behaviour and imports its functions, as `use TemporalSdk.Workflow` does (`include/workflow.hrl:1-123`, `lib/temporal_sdk/temporal_sdk_workflow.ex:5-11`); a name is a binary (`<<"Approve">>`, `~"Approve"`), a user type a map with binary keys, and process-dictionary state `put/2` and `get/1`. Paths below are in `temporal_sdk` source at `d2749c7`.

## Project roots

- A `mix.exs` whose `deps` lists `{:temporal_sdk, …}`, or a `rebar.config` whose `{deps, …}` lists `temporal_sdk`, marks a root that uses Temporal. Its app name (`app:` in `mix.exs`, the `.app.src` application in rebar3), else the repo path, is the path `twf mod init` takes; ask when neither fits. Each app of a mix umbrella (`apps/*/mix.exs`) or a rebar3 multi-app project (`apps/*/src/*.app.src`) is its own root; `test/` and `test/support/` hold tests and their fixtures, not the design.
- A Hex requirement (`{:temporal_sdk, "~> 0.2"}`, a bare `temporal_sdk` in rebar3) is a BUSL-1.1 release. The design reads the same; tell the user before generating against it ([SKILL.md](../SKILL.md#orient)).

## Registration

- `TemporalSdk.Worker.start(cluster, :workflow | :activity, opts)`, in Erlang `temporal_sdk_worker:start/3` (`worker/temporal_sdk_worker.erl:444-454`), starts a worker on its `task_queue:` in its `namespace:`, `"default"` when unset (`worker/temporal_sdk_worker_opts.erl:154-155`). So does each entry of a cluster's `workflows:` and `activities:` lists in the application config, `config :temporal_sdk, clusters: [c: [workflows: [[task_queue: "q"]]]]` in `config/*.exs` or `{temporal_sdk, [{clusters, …}]}` in `sys.config` (`docs/cluster/-module.md:25-29`). The workflow and activity workers on one queue and namespace make one `worker` block. A queue or namespace read from the environment (`System.get_env`, `os:getenv`) cannot be resolved from code: ask, or leave it to the stitch's topology. The other options read back through [options.md](./options.md#worker-options) into the namespace worker's `options:`. Follow a helper that wraps the start (the corpus's `Corpus.Temporal.start_worker/5`) to the start call.
- A worker's types are its `allowed_temporal_names`, each the module its `temporal_name_to_erlang` maps it to ([worker.md](./worker.md#registration)). A `workers.ex` `start_<worker>` and its name→module maps make `worker <worker>`, annotated `@sdk(elixir, "<path>")` with that file, from the directory of the nearest `twf.mod`, else the `.twf` file's directory. In Erlang, the module whose `start_<worker>` makes those starts is the same set, annotated `@sdk(erlang, "<path>")`. A test's worker gives the test's queue, not the deployment's, and modules only tests start are fixtures.
- A worker left unrestricted, `allowed_temporal_names` unset (`worker/temporal_sdk_worker_opts.erl:158`), serves every loaded module its name resolves to with `binary_to_existing_atom` (`api/temporal_sdk_api.erl:591-615`), or those `allowed_erlang_modules` lists (`:159`). Its types are then the modules callers name: an atom sends its own name (`temporal_sdk/temporal_sdk_workflow.erl:1769-1772,2058-2059`). An Erlang module `process_order` is the `.twf` name `process_order`, but an Elixir module's name, `"Elixir.Orders.ProcessOrder"`, is no `.twf` identifier: record it, and tell the user the code needs a mapping before a `.twf` can name it.
- A module with `use TemporalSdk.Workflow` (`-behaviour(temporal_sdk_workflow)`) is a `workflow`: its params are the elements of `execute/2`'s input list, positional (`[order, item]`), and its result is what it closes with. A `use TemporalSdk.Activity` module is an `activity`: its `execute/2` returns the result's payload list, `[r]`, or `[]` for none ([activity-def.md](./activity-def.md)). Param and result types come from a `@spec`, `@type` or doc where one names them, else from the values ([types.md](./types.md)).
- `Arrivals.on("Name", fn [a, b] -> body end)`, on the project's copy of `Arrivals`, declares `signal Name(a, b)`, its body the function's; `fn _ ->` binds no params ([signal-handler.md](./signal-handler.md)). A name awaited raw, `{:signal_request | :signal_admit | :signal, "Name"}` (`temporal_sdk/temporal_sdk_workflow.erl:1208-1213`), declares the signal too; its handler body is what the code does with each arrival. The process-dictionary keys that signal bodies and queries read, set at the start of `execute/2`, are its `state:`, camelCased (`:last_transaction_id` → `lastTransactionId`), less `Arrivals`' own entries.
- A `start_execution(:f)` whose `f` awaits `{:query_request, "Name"}` and answers `respond_query({:query, "Name"}, answer: [v])` declares `query Name(params) -> (T)`: its params are the request's `query_args`, and its body returns the state behind `v`, which the main execution publishes with `set_info(value, info_id: id)` and the query reads with `is_awaited({:info, id})` ([query-handler.md](./query-handler.md)). A `handle_query/2` clause answers the same query for a closed run; with no open-run loop for its name, record its answer in prose.
- A public `id/n` on a workflow's module, interpolating its args into the `workflow_id:` every start passes, is its `id_scheme:`, each hole named from the workflow's params (`ShipItem.id(order["id"], item["id"])` → `"ship-{order.id}-{item.id}"`). A `start_options` function's `workflow_id_reuse_policy:` and `workflow_id_conflict_policy:` atoms are its `default_options:` ID policies ([workflow-def.md](./workflow-def.md#id_scheme)).
- A keyword-list function that every call of one activity or workflow starts from (`defaults()`, `@activity_opts`) is that definition's `default_options:`; the keys a call merges in with `Keyword.merge/2` or appends are that call's `options:` ([options.md](./options.md#definition-level-default_options)). `input:`, `workflow_id:`, `awaitable_event:` and `wait:` are call mechanics, not options.
- A queue built by an instance-key function (`def sandbox_queue(id), do: "sandbox-" <> id`) is a [family](./worker.md#per-instance-worker-families) worker.
- A `:nexus` worker (a `nexuses:` entry) serving `@behaviour :temporal_sdk_nexus` modules, `start_nexus/5`, `handle_message/3`, a wildcard `{:signal_request, :_}`, `cancel_activity/1`, `cancel_workflow_execution/1`, `modify_workflow_properties/1`, and a `start_execution` that is no query loop have no `.twf` form at the pin ([nexus.md](./nexus.md), [nexus-service-def.md](./nexus-service-def.md)): record each in prose with its `file:line`.

## Concurrency

| Elixir | `.twf` |
|--------|--------|
| `[a, b] = Arrivals.take("X")`; `Arrivals.take("X")` | `await signal X -> (a, b)`; `await signal X`, binding none ([await-signal.md](./await-signal.md)) |
| `p = Arrivals.promise("X")`, `Arrivals.await(p)` later | `promise p <- signal X` ([promise.md](./promise.md)) |
| `wait({:signal, "X"})` or `wait({:signal_request, "X"})`, without `Arrivals` | `await signal X`, with a comment that arrivals collapse: the index holds only the latest, and stays ready after it, `{:signal_request, "X"}` until `admit_signal` (`api/awaitable/temporal_sdk_api_awaitable_index.erl:381-384,863-868`) |
| `start_activity(…, wait: true)`, `start_child_workflow(…, wait: true)`, `wait(start_…(…))` | synchronous call; the `fail_workflow_execution` its non-`:completed` states close with is the call's failure failing the run, not a `close fail` ([activity-call.md](./activity-call.md)) |
| `p = start_activity(…)`, `start_child_workflow(…)` or `start_timer(d)`, without `wait:`, `wait(p)` later | `promise` ([promise.md](./promise.md)) |
| `wait_all([...])`; over `Enum.map` | `await all`, branches in list order; a `for` fan-out inside ([await-all.md](./await-all.md)) |
| `Arrivals.first(a: …, b: …)`, re-ranked after each `await_any` | `await one`, cases in keyword order ([await-one.md](./await-one.md)): `ready_at` then `claim` a signal case, `task_at(p)` an activity, child or promise case, and `ready_at` never claimed a condition its signal's body sets ([composite-patterns.md](./composite-patterns.md)). A timer started for this race alone is a `timer(d)` case, its `cancel_timer` when it loses part of the race; one started earlier and passed across rounds is `promise t <- timer(d)` with a `t:` case |
| `await_any([...])`, then a pick by whichever is ready | `await one`, with a comment that the first ready at this wake-up wins, which is not replay-safe across tasks ([await-one.md](./await-one.md)) |
| `await(p, d)` or `await_any(list, d)` | `await one` with `p`'s case first, then `timer(d)`, holding the `{:noevent, _}` branch: `p` ready in the timer's task wins, and the timer is cancelled when `p` wins (`temporal_sdk/temporal_sdk_workflow.erl:2563-2586`) |
| `Process.put(:flag, false)`, set in a signal body, then `await_condition(names, fn -> Process.get(:flag) end)` | `condition` + `set` / `unset`, and `await flag` ([condition.md](./condition.md)) |
| `start_child_workflow` with `parent_close_policy: :PARENT_CLOSE_POLICY_ABANDON`, `awaitable_event: :start` and `wait: true`, `:initiate_failed` failing the run, then `await_open_before_close(false)`, the result never read | `detach workflow` ([detach.md](./detach.md)) |
| `continue_as_new_workflow(tq, "W", input: [...])` in `W` | `close continue_as_new(args)` ([close.md](./close.md)); onto another type, record it in prose |
| `start_timer(d, [:wait])` | `await timer(d)` ([await-timer.md](./await-timer.md)) |
| a `record_uuid4`, `record_system_time` or `record_rand_uniform` marker | the value as an assignment, `jobId = uuid()` (`temporal_sdk/temporal_sdk_workflow.erl:2374-2424`) |

## Codegen

- No forward variant generates code ([SKILL.md](../SKILL.md#orient)). The SDK's own `lib/` is an Elixir wrapper generated from its Erlang API (`lib/temporal_sdk/temporal_sdk_workflow.ex:2-3`), not part of a design.
- Under the default converter a payload is plain data ([types.md](./types.md)): a map, string- or atom-keyed, is a user type keyed by its field names as written; `:null` an optional; a binary a `string`, or `bytes` where it is not UTF-8 or is base64'd. A string or integer is `decimal`, `time` or `duration` only where a name or comment says so. A custom codec chain on the cluster's `client: [grpc_opts: [converter: …]]` changes the encoding, not the types.
- A `mix.exs` `compilers:` entry or a `rebar.config` plugin or provider hook names any other generator.
